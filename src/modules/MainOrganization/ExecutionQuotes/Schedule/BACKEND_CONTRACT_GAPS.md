# Remaining backend contract questions

The endpoint names, request keys, numeric TaskDurationType values, Quote ownership, Configuration save/upsert and `change_projecttimeline_order` body are confirmed. They are not outstanding questions.

1. **Mutation responses:** provide actual success/error bodies and HTTP statuses for `store_project_timeline`, `update_project_timeline`, `delete_project_timeline`, `change_projecttimeline_order` and `store_project_configuration`. Include message-only/no-data success and validation field paths, authorization/frozen-history, missing-record and conflict failures. The repository now uses the application’s existing BaseRepository response convention; these Schedule-specific response examples have not been verified.
2. **Configuration responses:** provide the `show_project_configuration` envelope and saved/missing examples, including `start_date` and primitive `holidays`. Distinguish missing configuration from persisted `holidays: []`; clarify nullable/omitted fields and whether date clearing is supported. The current form sends a required date-only string, not null.
3. **Returned Stage identity:** is timeline `stages[].id` the QuoteStage association ID accepted as `quote_stage_id`, or a timeline-selection record ID? In the supplied example it is 3 while `stage.id` is 129. If it is a selection record, supply the actual QuoteStage ID field. Request `children[]` uses the direct Quote SubStage association ID from Quote Show. Which timeline-response field identifies that same association? The nested `sub_stage.id` is a master label ID and must not be assumed to be the request ID. Response-derived Edit is guarded until this is resolved; no master Stage ID is substituted.
4. **Show envelope:** confirm whether `show_project_timeline` returns the supplied item directly as the HTTP body or inside an envelope. The current parser supports the supplied direct item only.
5. **Complete sequence:** confirm whether Fetch is always unpaginated and ordered, whether `basicData.count_timeline` is the total timeline count, and any pagination metadata/read parameters. The current implementation does not reorder a result whose returned length differs from its count and does not invent pagination controls.
6. **Status and dates:** provide actual status values and server-calculated overall finish/per-timeline start/finish field locations, formats and unavailable values. The supplied example has only basic start date and null status. No frontend calendar, duration conversion or finish date is fabricated.
7. **Selection edge cases:** define request `children: []` semantics, and whether returned child `sub_stage` may be missing/null. Such returned child values are currently rejected to avoid inventing a SubStage identity; parent `sub_stage: null` is supported.
