## Router implementation

The router is created in [`src/router/index.ts`](../../src/router/index.ts) with `createWebHistory(import.meta.env.BASE_URL)`. Route components are lazy-loaded. Protected route targets mount [`src/views/AppLayout.vue`](../../src/views/AppLayout.vue), which renders [`DashboardLayout.vue`](../../src/shared/LayoutComponents/DashboardLayout.vue) and its nested `RouterView`.

There are 160 configured `RouteRecordRaw` records:

- 7 top-level records.
- 63 children below `/admin`.
- 90 children below `/organization`.
- 149 distinct absolute URL patterns after accounting for duplicate child paths.

The duplication is source-confirmed: the admin parent receives 10 unsuffixed admin routes plus all 53 shared routes, even though the first 10 are also in the shared array. The organization parent receives 37 dashboard records plus 53 shared records; `system-identity` occurs in both. The tables below preserve this configuration rather than deduplicating it.

## Access rules used in the tables

The global guard requires the persisted authentication flag, a usable API token, a recognized `UserType`, route role metadata, and the matching URL prefix:

- `/admin` declares `allowedUserTypes: [UserType.ADMIN]` and requires value `1`.
- `/organization` declares `allowedUserTypes: [UserType.ORGANIZATION]` and requires value `2`.
- The three administrator CRUD child records declare `allowedUserTypes: [UserType.ADMIN]` even when shared expansion places copies under `/organization`.
- The only unauthenticated destinations allowed by the guard are `/login-admin` and `/login-organization`.
- `isMaster`, sidebar `roles`, and the placeholder `PermissionBuilder` do not add route-level authorization. No granular action permission metadata exists.

Query parameters are not declared in route definitions. The “Query parameters” column lists only values read by the mounted implementation.

Repeated access/layout values are summarized here rather than duplicated across every child row:

| Route collection         | Layout                          | Required authentication                                    | Required permission/role                                                       | Collection-level redirect behavior                          |
| ------------------------ | ------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| Top-level login          | `AuthShell` inside each view    | No; authenticated users with a usable token are redirected | No login-page permission; existing type chooses redirect target                | Guard redirects to the user's mapped app                    |
| `/admin` children        | `AppLayout` → `DashboardLayout` | `isAuth`, usable token, and recognized type required       | `UserType.ADMIN` (`1`) through parent metadata                                 | Wrong recognized type → `/organization`; no child redirects |
| `/organization` children | `AppLayout` → `DashboardLayout` | `isAuth`, usable token, and recognized type required       | `UserType.ORGANIZATION` (`2`), except admin CRUD child metadata requires admin | Wrong recognized type → `/admin`; no child redirects        |
| Not-found/catch-all      | None                            | Guard requires a complete local session outside login      | Any recognized type                                                            | Catch-all → `/not-found`; incomplete/absent session → login |

## Breadcrumbs and route metadata

Child records set `meta.breadcrumb` and, for add/edit/detail screens, often `meta.parent`. [`RouteHelper.ts`](../../src/shared/LayoutComponents/SubComponents/RouteHelper.ts) builds the feature header/breadcrumb from those values. Several values are plain English while system identity/toggle use i18n keys. Breadcrumb metadata does not control access.
